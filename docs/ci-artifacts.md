# CI Artifacts

[中文](ci-artifacts_ZH.md)

The ESP-IDF workflow has a 48-row source-build matrix: six shared examples on
two ESP-IDF versions (12 rows), plus six display examples for three distinct
display variants on two ESP-IDF versions (36 rows). The 8-inch and 10.1-inch
variants remain separate because their panel initialization tables differ.

ESP-IDF v5.5.5 rows compile only. Each ESP-IDF v6.0.2 display row uploads one
source-built ZIP, for 18 downloadable Actions artifacts on a full run. Open the
workflow run in the GitHub Actions UI and download the named artifact, or use:

```sh
gh run download <run-id> --name '<artifact-name>'
```

That CLI command expands artifact contents locally. The helper instead downloads
the original transport ZIP by artifact ID, so it can compare that ZIP with the
Actions artifact digest before extraction.

On Windows, run `Flash-CI-Firmware.cmd -Product lcd-7` (or `lcd-8` or
`lcd-10-1`). Running it without `-Product` opens a model selector. `-ListOnly`
lists the supported products and six display examples without network access or
state changes; `-SelfTest` is an offline, device-free contract test.

The helper accepts only ESP-IDF v6.0.2 source-built display artifacts for the
current branch head and selected product. Before download it requires a clean,
non-detached branch with an upstream, exactly one non-draft open PR at that
head, and one successful exact-SHA workflow run containing all six unique,
unexpired SHA-256 artifacts. It downloads the original transport ZIP by artifact
ID and, before extraction, compares it against GitHub Actions' artifact SHA-256
digest, then verifies ZIP paths, checksums,
manifest identity, split offsets, the 32 MB NOR address range, and safe
`flash_args`. A supplied `-Port` takes precedence over a valid saved port for the
same product and SHA; otherwise the helper uses that saved port before USB
auto-detection. Merged images
are checked but never written directly. A successful transfer must report
`Hash of data verified`; only then can the operator mark the example PASS and
advance the saved progress.

Each non-destructive `chip_id` probe must report both an ESP32-P4 revision and
a MAC address. The helper normalizes that MAC and binds saved progress to it;
any missing MAC or changed revision/MAC identity fails closed before flashing.

Artifacts are retained for 14 days. They are source-built examples, not factory
firmware or release images and not a replacement for the versioned
`firmware/*-FactoryOnly-*.bin` files. This helper performs no hardware-in-the-loop validation; operator PASS
records a manual check only.
## Silicon-revision profiles

Example artifacts are `rev3_x` only, without doubling the 48-row example
matrix. `rev1_3` is the explicit source-build profile for revision 1.x silicon,
including v1.3; it selects a minimum of 1.0 and the pre-v3 hardware group.
`rev3_x` selects a minimum of 3.0 and is the repository default. The two groups
are mutually exclusive and their binaries cannot be exchanged. See
[ESP32-P4 Silicon Revisions](silicon-revisions.md) for the configuration and
hardware-facing differences. Each package records schema version 2, the fixed
32 MiB flash capacity, profile/bounds, numeric split offsets, file sizes,
SHA-256 values, and separate merged-image metadata. Published names use the
exact checkout SHA12. A successful compile is not hardware validation.

`firmware/brookesia` is the maintained product firmware source. Its dedicated ESP-IDF v5.5.5 workflow builds three Rev3.x artifacts: lcd-7, lcd-8, and lcd-10.1. The Windows helper rejects Rev1.3 hardware because this exact-head CI surface publishes no Rev1.3 artifacts. The dated FactoryOnly BIN files are separate immutable deliveries and are not regenerated by CI. `11_esp_brookesia_phone` remains covered by the regular example matrix.

The [Arduino examples workflow](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-X/actions/workflows/arduino-examples.yml)
is a separate 30-row compile matrix: 10 sketches for LCD-7, LCD-8, and
LCD-10.1, using Arduino CLI `1.5.1` and Arduino-ESP32 `3.3.11` with the
`postv3` Rev3.x board profile. Only `04_LVGLV9` uses the bundled LVGL `9.5.0`
configuration. The workflow produces no Actions artifact, release image, or
factory firmware. A successful compile is not a hardware test; `05_WiFiAnalyzer` also needs compatible
ESP32-C6 hosted firmware when run on a board. See the [Arduino examples
guide](../examples/arduino/README.md) for the sketch list, board options, and
hardware-validation boundary. CI uses the same self-contained
`examples/arduino/libraries` tree provided for Arduino IDE users; it does not
download an Arduino library during the build.
